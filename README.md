# Мини-CRM «Объекты и задачи»

Приложение для строительной команды: постановщик создаёт объекты, распределяет задачи и проверяет результат; исполнитель работает только со своими задачами. История переходов сохраняется автоматически.

Стек: React, TypeScript, Vite, Material UI, React Router, TanStack Query и Supabase. Версии зафиксированы в `package-lock.json`. Supabase для разработки работает в Docker; облачный аккаунт для локального запуска не нужен.

## Быстрый локальный запуск

Нужны Node.js 22.12+ и работающий Docker Desktop с Linux-контейнерами. На Windows при ограничениях PowerShell используйте `npm.cmd` и `npx.cmd` вместо `npm` и `npx`.

```sh
npm ci
npm run db:start
node scripts/configure-local.mjs
npm run demo:local
npm run dev
```

Откройте **http://127.0.0.1:5187**. Порт закреплён за этим проектом; занятый порт вызывает ошибку, а не незаметный запуск на другом адресе.

Первый запуск Supabase скачивает Docker-образы. Настройка создаёт `.env.local` с публичным ключом и `.env.test` с локальными тестовыми ключами. Существующий `.env.local` не перезаписывается.

`demo:local` создаёт три демонстрационных аккаунта, три объекта и семь задач во всех пяти статусах. **Email и случайные пароли находятся в `.cache/demo-access.local.json`**. Файл исключён из Git. Повторный запуск не создаёт дубликаты и не сбрасывает пароли. История демонстрационных задач формируется через те же RPC, что использует приложение.

Чтобы остановить локальную базу с сохранением данных:

```sh
npx supabase stop
```

Приложение останавливается `Ctrl+C` в терминале с Vite. Для повторного запуска достаточно `npm run db:start` и `npm run dev`.

## Команды проверки

```sh
npm run typecheck
npm run lint
npm test
npm run test:api
npx playwright install chromium
npm run test:e2e
npm run build
npm run format:check
```

- `npm test`: PostgreSQL через PGlite, матрица ролей/статусов, RLS, история и загрузка списков по страницам. Docker не требуется.
- `test:api`: настоящий локальный Supabase, пользовательские JWT, вложенные запросы, подделка истории, конкурирующие переходы и закрытая регистрация. Требуется `.env.test`.
- `test:e2e`: Chromium, полный цикл задачи, переназначение, удаление, выход, мобильный вход и неверный пароль. Запускает собственный Vite на 5187: перед этим остановите уже запущенный `npm run dev`.
- API/E2E-фабрики создают и удаляют только свои тестовые записи. Они отказываются работать с адресом вне `localhost`/`127.0.0.1`.
- Отчёты и трассы Playwright находятся в игнорируемых `playwright-report/` и `test-results/`. Трассы могут содержать тестовые сессии: не публикуйте их.

Для воспроизведения миграций на **пустой локальной базе**:

```sh
npm run db:reset
npm run db:types
```

`db:reset` удаляет локальные данные, включая демонстрационные. После осознанного сброса удалите только `.cache/demo-access.local.json` и выполните `npm run demo:local` заново. Для облачной или рабочей базы эту команду не используйте.

## Авторизация и безопасность

- Регистрация и анонимный вход выключены (`supabase/config.toml`). Роль выдаётся только записью в `profiles`.
- RLS на всех таблицах; запись только через RPC в `crm_private`. Исполнитель видит лишь свои задачи и связанные объекты.
- История статусов неизменяема через пользовательский API. Фронтенд использует только `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY`.

Правила и права — в `supabase/migrations/202611040001_crm.sql`. Типы — `src/lib/database.generated.ts` (`npm run db:types`). Вторая миграция добавляет `revision` для оптимистичных правок: устаревшая форма не затирает чужие изменения. Подробнее — [docs/decisions.md](docs/decisions.md).

## Правила работы

| Действие                                            | Разрешение                        |
| --------------------------------------------------- | --------------------------------- |
| Создание, редактирование, удаление объектов и задач | Любой постановщик                 |
| Новая → В работе                                    | Назначенный исполнитель           |
| В работе → На проверке                              | Назначенный исполнитель           |
| На проверке → Принята                               | Любой постановщик                 |
| На проверке → На доработке                          | Постановщик, непустой комментарий |
| На доработке → В работе                             | Назначенный исполнитель           |

Остальные переходы запрещены. Обычное редактирование не меняет статус, автора или дату создания.

Согласованные особенности:

- Удаление мягкое. Объект скрывается вместе с задачами; история остаётся в базе. Интерфейса восстановления нет.
- Переназначение возможно в любом статусе без его изменения. Старый исполнитель сразу теряет доступ на сервере, новый видит всю историю.
- Имя автора, имя участника истории и имя назначенного исполнителя сохраняются как снимки. Это позволяет показать имена без открытия исполнителю справочника коллег.
- Описание необязательно. Названия, адрес и назначение обязательны. Комментарий из пробелов/переводов строки не считается заполненным.
- Даты хранятся с часовым поясом, отображаются по часовому поясу браузера.
- Данные обновляются после действий, при возвращении на вкладку и каждые 15 секунд. Realtime не используется. При выходе клиентский кеш очищается.
- Списки и история загружаются порциями по 500 строк, чтобы не обрезаться стандартным лимитом Data API.

## Развёртывание вне компьютера

**Локальный Docker не является публичным сервером.** Vercel не сможет обращаться к `127.0.0.1` вашего компьютера. Для доступной проверяющим ссылки нужен облачный Supabase либо Supabase, размещённый на доступном сервере с HTTPS. Конфигурация Supabase CLI в этом репозитории предназначена для локальной разработки, а не для публичного production-сервера.

После подготовки внешнего Supabase:

1. Примените SQL-миграции. Для облачного проекта можно использовать `npx supabase login`, `npx supabase link --project-ref PROJECT_REF`, `npx supabase db push`. Для собственного сервера примените миграции к его PostgreSQL административным инструментом.
2. Отключите открытую регистрацию и анонимный вход в целевой системе. Убедитесь, что email/password включён, а `crm_private` не экспонируется через API. Локальная настройка автоматически не переносится в облако.
3. Создайте пользователей через административную панель Auth. Выдайте роли записью в `profiles`, например:

```sql
insert into public.profiles(id, display_name, role)
values ('UUID_ПОЛЬЗОВАТЕЛЯ_ИЗ_AUTH', 'Имя пользователя', 'dispatcher');
```

Для полностью нового демонстрационного проекта можно вместо ручного наполнения скопировать `.env.seed.example` в `.env.seed`, заполнить параметры и выполнить `npm run demo:seed`. Скрипт создаёт только демонстрационные аккаунты; секреты и полученные пароли остаются вне Git.

4. Создайте репозиторий GitHub и отправьте исходники. Не добавляйте `.env*`, `.cache/` и тестовые трассы.
5. Импортируйте репозиторий в Vercel как Vite. Установите две **публичные** переменные `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY` для выбранной среды; сборка — `npm run build`, каталог — `dist`. Настройка SPA-маршрутов уже есть в `vercel.json`.
6. После публикации проверьте вход всеми тремя аккаунтами, обновление вложенного URL, работу переходов и изоляцию исполнителей. Пароли передайте проверяющему отдельно от репозитория.
